# 中转层(RPC 映射/转发层)设计方案

> 需求来源:`D:\project_code\1927test\需求`
> 目标:在不改动 1927 主控层(mctrl/gui)任何代码、不感知的情况下,让主控层"指挥"28 模型界面运动、拍照并拿到视觉/共焦(cf)结果。
> 本文所有协议细节均来自对两侧代码/文档的直接阅读,证据附文件路径;凡需现场验证之处以 **【待确认】** 标出。

---

## 1. 结论摘要

主控层(1927project)通过 **ISTAR 平台自研 RPC(底层 ZeroMQ + 二进制序列化,预编译 DLL)** 调用 motion1~4 与 io 共 5 个服务端;视觉与共焦(cf)通过 **MQTT** 通信。28 模型是**单进程自包含的下位机仿真**(HTTP/WS/MQTT/TCP 若干服务,全部回环 127.0.0.1)。

**中转层 = 一层"协议翻译代理"**,做三件事:

1. **复刻 5 个 ISTAR RPC 服务端**(motion1~4 + io),监听与真机完全相同的端口、用同一套预编译接口库(而非裸写协议),把主控发来的调用翻译成 28 模型 HTTP/MQTT 调用;
2. **做 MQTT 桥**:同一 broker(127.0.0.1:1883)上,收主控的视觉/共焦请求 topic,把 28 模型的拍照/共焦结果翻译回主控协议;
3. **主控侧"主动上报"原样复刻**:motion/io 的心跳、Observer、命令完成推送照常发布;28 模型结果(视觉/共焦)应答式回传。

部署时仅替换 `start_all.bat` 中的 5 行(`CTL_MDL_IO` + 4×`CTL_MDL_Motion`),**不新增/修改任何 1927 侧配置文件**;28 模型正常启动即可。

## 3. 两侧现状(事实基础)

### 3.1 主控侧(1927project)

```
GUI.exe ──RPC 35000──▶ mctrl(MCtrl.exe) ──┬─RPC▶ motion1..4 (35200/35210/35220/35230 组)
                                           ├─RPC▶ io (35100 组)
                                           ├─RPC▶ mc/eh/rp/rm/rm2 (20100/21400/21700/20000/20010,不在本次范围)
                                           └─MQTT(1883)▶ VSC_Com / CTL_WM_CF_ControlManager
视觉/共焦结果 ◀──MQTT VSS_Com / CTL_DR_CF_FLS
```

- **地址唯一来源**:`config/mw_config.yaml` 的 `middleware.<模块名>` 段(sync_mw_config.bat 向各子工程散布);MQTT broker 在 `config/mctrl/appconfig.yaml`(`127.0.0.1:1883`)。
- **RPC 协议**:ISTAR 平台(预编译 `ISTARMW.dll`/`ISTARZmqWorker.dll`/`ISTARSerializer.dll` 等,头文件在各 `basiclibrary_output/include`)。方法→32 位 hash funCode;ZMQ TCP;**帧/序列化在闭源 DLL 内** —— 这是"中转层必须链接同一套接口库、不能裸写协议"的根本原因。
- **端口布局**(每模块占用 P、P+1、P+3 三个端口):

| 模块 | config.json moduleName | REP/REQ | ROUTER/DEALER | PUB(motion/io 推送给客户端) |
|---|---|---|---|---|
| motion1 | motion1 | 35200 | 35201 | 35203 |
| motion2 | motion2 | 35210 | 35211 | 35213 |
| motion3 | motion3 | 35220 | 35221 | 35223 |
| motion4 | motion4 | 35230 | 35231 | 35233 |
| io | io | 35100 | 35101 | 35103(io 服务端另有 SUB 35102 收外部 publish,由 IOServerInit 自动绑) |

- **mctrl 判活**:每秒对每个下游发 `GetServerStatusAsync`,不回 `bSuccess=true` 即判 OFFLINE(RPCClientManager.cpp:157-174)——中转服务端必须正常应答(接口库默认骨架已回 success)。
- **mctrl 启动**:对 4 个 motion 同步 `MotionGetServerInfo`,按 `stageName` 字符串匹配内置枚举(motion_stage_id.h,与 config 的 stage 名一致)建 stage→client 映射;`stageType`/`systemName` 不校验,但 stageName 不匹配会 skip 并告警。

### 3.2 28 模型侧(28module/backend)

单进程 `runtime/main.py` 同时提供(全部绑 127.0.0.1):

| 端口 | 协议 | 入口 | 用途 |
|---|---|---|---|
| 9010 | HTTP REST + WebSocket | ws_gateway.py | `/api/axis/move|jog|home|config`、`/api/io/command`(PLC 代理)、`/api/axes`、`/api/confocal/read`、`/api/vision/acquire|identify`、`/api/flow/*` 等;`/ws` 500Hz 二进制轴位置帧(喂 HTML 前端动画) |
| 9101 | TCP 换行 JSON(ACS 指令面) | acs_tcp.py | `enable/disable/home/move/stop/getpos/status/...`(axis 名) |
| 9102 | HTTP JSON(PLC 语义层) | plc_http.py | `POST /io/command {path,cmd,args}`、`GET /io/observe?path=`、`GET /io/snapshot` |
| 9190 | HTTP JSON(Cordis MCS 五服务信封) | mcs_http.py | `getMachinePartProperties/executeCommand/getObserverValuesFromObserverPaths/...` |
| 1883 | 迷你 MQTT 3.1.1 | mqtt_broker.py | **视觉/共焦结果出口**:`vision/result/{cam}`、`confocal/result/{probe}`;服务端订阅 `vision/trigger/+`、`confocal/trigger/+` |
| 9200 | TCP 帧 | vision_service.py | 相机图像接收(REAL 模式渲染,一般用不到) |

- **关键约束**:28 模型 **QoS 支持有限**:SUBSCRIBE 一律授予 QoS0;PUBLISH QoS1 回 PUBACK 并转发;QoS0 直接转发;**QoS2 只回 PUBACK 不转发**(mqtt_broker.py:243-269)。见 §8.1 风险与对策。

### 3.3 28 模型与主控的"同名/同构"程度(好消息)

28 模型是为同一台 D2W 设备建模的,很多命名与主控**天然同源**(轴号、Cordis 路径、点位表):

- 主控 ACS 轴的控制器轴号与 28 模型 **ACS 轴号完全一致**:config1 WaferStage_XY(X=idx0/Y=idx2)、WaferStage_Rz(Rz=idx4)、config3 AlignStage_XY(6/7)、AlignStage_Z(8)、PunchZ(10)、config4 FA_X(9)。28 模型同号轴:WS_LS_X(0)/WS_LS_Y(2)/WS_Rz(4)/AS_X(6)/AS_Y(7)/AS_Z(8)/ES_PunchZ(10)/FA_X(9)。
- 点位表(1928运动固件点位表_V6)同时是主控 io 变量与 28 模型 `io_points.json` 的来源,真空/门锁/相机触发的 Cordis 命令/观测名一致(如 `AlignCameraTigger_1/2`、`AirRouteClose/...`、`oYN_XN_WithChip`...)。
- 轴坐标单位一致(**直线 mm、旋转 rad**,28 前端内部才是 deg)。

这使"轴映射表"有了可靠种子(§7),但**名称并非处处逐字一致**(如主控 ArmHead_* vs 28 BS_*、主控 FA_Rz vs 28 CH_Rz),需要一张**可配置映射表 + 联调标定**。

### 3.4 关于"28 模型也是 RPC 接口"的核实(2026-09-04)

28 模型开发同事提到"我们也是 rpc 接口",已向 28 模型工程核实,结论:

- 28 模型 **runtime(后端模型/*.py)没有任何 ISTAR/ZMQ 类 RPC、也没有类似我们 io/motion 驱动层的服务端**。它的"最外层入口"就是 §3.2 的五类:HTTP REST(9010)、ACS TCP(9101)、PLC /io/command(9102)、**MCS HTTP 五服务(9190,信封式 `/JsonServices/...`——这才是同事口中的 "RPC 接口")**、MQTT(1883)。
- 28 模型文档明确其自身定位是**下位机(机器)侧**,分层为 L1(GUI)↔L2(主控)↔L3(Motion/IO),且 **L2↔L3 的真机 RPC"技术栈未知、待确认(Q2)"**,仿真内部用的是自己定义的"过渡 RPC"能力面(接口规范_V1.md:9-21、62-74;仿真差距与路线图.md:66)。也就是说它**不存在"比我们映射目标更上层的一层封装"**,我们的翻译打到的就是它的最外层。
- 仓库 `部分接口信息/` 下的 io_template / motionstage_template / motion(带 .git/.gitmodules)是**同事模板工程的快照**(与 1927 的 module/io、module/motion 同构的驱动层工程),28 模型开发者把它作为"上位机 RPC 契约事实源"存档,**不是 28 运行时的组成部分**。
- 因此无需改设计,但有一处**层级偏好**值得吸收(见 §6.1):对 28 模型已建模的 PLC 运动轴,优先走 **MCS stage 命令面(9190,按 machinePart 全路径的 Enable/Home/MoveAbs,语义与真机 motion 驱动对齐)**;ACS 直驱轴(WS/AS/FA_X/PunchZ)在 MCS 树里没有 stage 节点,只能走 ACS TCP/`/api/axis/move`——这与真机一致(ACS 轴本就由上位机经 ACS SDK 直控,无中间 stage)。

## 5. 进程模型与工程组织

### 5.1 进程划分(贴近现状,便于替换)

| 进程 | 职责 | 占位 |
|---|---|---|
| RelayMotion.exe ×4 | 复刻 motion1~4 服务端:GetServerInfo/命令/观测 + 心跳/Observer/命令完成推送;把命令翻译给 28 模型 | config\motion\configN(config.json 的 moduleName 区分端口) |
| RelayIo.exe ×1 | 复刻 io 服务端:GetServerInfo/读 DO-DI/SetDo.../心跳/Observer/SetCompleted;DO 写翻译成 28 模型 PLC 命令或相机触发 | config\io |
| RelayBridge.exe ×1 | MQTT 桥:主控视觉(VSC_Com/VSS_Com)+ 共焦(CTL_WM_CF_ControlManager/CTL_DR_CF_FLS)与 28 模型视觉/共焦 topic 双向翻译;无 RPC 端口 | 无(纯 MQTT) |

RelayMotion/RelayIo 与 RelayBridge 共享一个**内核库**(映射表加载、28 模型 HTTP/MQTT 客户端、状态轮询、触发→结果配对)。之所以 RPC 代理与 MQTT 桥分开:RelayBridge 需要独立处理"拍照触发→结果 1:1"的有状态队列,且不依赖 config.json 的 moduleName 机制。

> 备选:把 4+1 个 RPC 代理合并成单进程多 server(接口库支持按 moduleName 多次 Init),但需验证单进程内多套 server 线程/端口互不干扰;为贴近 `start_all.bat` 的"每配置一进程"模型并降低风险,首推多进程。

### 5.2 实现语言与依赖(关键决策)

- **语言**:C++(MSVC 2017,与 1927 工程同工具链;**不需要 Qt**——协议基类与 fake_mctrl 先例均为纯控制台)。
- **RPC 半边**:链接预编译库
  - 服务端基类头/库:`module/motion/interface/include/*` + `module/motion/interface/lib/{motion.lib,motion.dll}`;`module/io/interface/...`。
  - 派生 `UIMotionControllerServerImpl` / `UIIoControllerServerImpl`,覆写虚方法(`motion_server.h:90-140` 等);初始化 `MotionServerInit(mw_config.yaml, moduleName)`/`IOServerInit(...)` 自动绑定 REP/ROUTER/PUB(SUB)端口;回包仅需填 `response.bSuccess/errorCode/data` 并 `return ISTAR_RESULT_SUCCESS`。
  - **先例**:`gui/testtools/fake_mctrl`(继承 `UIMControllerServerImpl` 的纯控制台假服务端,工程/构建配方可直接照搬,把 mctrl.lib 换成 motion.lib/io.lib);`module/motion/.../StageServer/StageServer.cpp` 是"覆写 + 调 `Motion*Publish`"的现成样板。
- **MQTT 半边**:链接 `ISTARMqtt.dll` 等(照抄 `mctrl/VisionCFSim` 工程),用平台 `TaskInfo` 信封结构(`istar_task.h`)与 `to_rawJson/from_rawJson`;28 侧 topic 用同一客户端发裸 JSON 字符串即可(平台 Publish 接受任意 payload)。
- **编译产物部署**:exe/bin + 全套平台 DLL(复制自 exe/lib/platform)+ 各自工作目录下的 `mw_config.yaml`(用 1927project/config 那份,只读)。

## 6. 映射详细设计

### 6.1 motion(主控 ISTAR RPC ↔ 28 模型运动)

主控每个 motion 模块下有多台 stage(motion1 硅片台:WaferStage_XY/Rz + EPIN_Z 等)。映射分两层:**stage→28 轴组**(§7 映射表),**每个请求方法→28 动作原语**:

| 主控请求(ISTAR) | 语义 | 28 模型动作(按映射轴逐轴/按 stage) | 完成判定(推 CmdCompleted) |
|---|---|---|---|
| MotionGetServerInfo | 发现 | 无 | 直接返回映射表登记的 stage/axisNames(config 一致) |
| MotionCmdEnable/Disable | 使能 | ACS 轴→9101 `{"cmd":"enable","axis":...}`;PLC 轴→9102 路径命令 Enable / MCS executeCommand | 轮询 /api/axes:该组轴 `enabled` 翻转完成 |
| MotionCmdHome | 回零 | 9101 `home` 或 /api/axis/home(mode 按轴配置) | 轮询该轴 `home_state=="done"`/`state=="idle"` |
| MotionCmdMoveAbs/MoveRel | 移动 | 按映射轴逐个/按 stage 下发;PLC 轴(在 mcs_map 有 axis_stage 节点,如 E_EPIN_Z、键合头、FA 轴)走 **MCS executeCommand(9190,stage 命令面,与真机驱动语义对齐)**;ACS 直驱轴(WS/AS/FA_X/PunchZ)走 `/api/axis/move {axis,target,speed}`(或 9101);EPIN 别名整组用 28 别名 `E_EPIN_Z` 一次驱动 3 针 | 轮询 /api/axes(PLC 轴也可轮询 MCS observer `oMoving/oInPos`):`moving==false && in_position==true`(有 tolerance 则按 \|pos−target\|≤tol),超时(默认 30s / 请求 timeoutMs)→ errorCode=1 |
| MotionCmdStop | 停止 | `/api/axis/move` 无 stop → 用 9101 `{"cmd":"stop",axis:...}` 或 PLC Halt | 轴 `state==idle`;被 Stop 打断的完成推 errorCode=2 |
| MotionCmdResetError | 清错(即时,无完成推) | 9101 `reset_error` / PLC Reset Error | 即时回包 |
| MotionCmdJog | 点动 | `/api/axis/jog {axis,delta}`(delta 换算) | 即时回包(主控当即时用) |
| MotionCmdSetVelAcc/SetDec/SetJerk/SetKillDec | 速度参数 | `/api/axis/config`(vmax/amax/jerk 等)或忽略(返回成功) | 即时 |
| MotionGetPos/Vel/Acc/Enable/Moving/InPos | 观测 | forceRefresh=false 用本地缓存 / true 现查 /api/axes | 按映射轴聚合;acc 28 无字段→用缓存差分或 0【待确认 GUI 是否用 acc】 |
| MotionCustomCommand/GetClientStatus/GetServerStatus | 预留/平台 | 记录日志;GetServerStatus 必须回 success | — |

- **主控异步模型**:请求立即 ACK;完成经 PUB 推送 `MotionCmdCompleted{stageName,cmdName,success,errorCode}`。因此转发进程内要有**命令台账(per-stage watcher)**:发起 28 动作后开轮询线程(20~100ms 周期),到判定条件后发布完成。
- **后端动作原语选择(§3.4 核实的"28 也是 RPC"结论的落点)**:28 模型的"最上层封装"分两类——MCS stage 命令面(9190,信封式 RPC,语义=真机 motion 驱动,仅覆盖 7 个 PLC 轴)与"过渡 RPC"能力面(9010 `/api/*`)。映射表为每根轴登记 `backend ∈ {mcs, api_axis, acs_tcp}`,实现期按轴可配:**PLC 轴默认 mcs、ACS 轴默认 api_axis/acs_tcp**,不以"统一走 /api"简化掉 28 自己的 stage 层;若某轴走 mcs 在联调中不可用(如 MCS 前缀未对齐,§8.5),退回 api_axis。
- **主动上报(复刻)**:1s `MOTIONStatusUploadPublish()`(平台无参心跳,与真 motion 服务端一致);500ms `MotionObserverDataPublish(StageObserverDataList)`,数据来自缓存(轮询 /api/axes 更新:pos/vel→轴状态聚合,enable=全轴与,moving=任一动,inPos=全轴到位);阶段常量照 config.json 的 `observerPeriodMs=500`。
- **GetPos 单位**:28 返回 mm/rad,与主控一致;旋转轴若有单位出入由映射表 `unitScale` 校准(§7)。

### 6.2 io(主控 ISTAR RPC ↔ 28 模型 PLC/命令面)

主控 io 服务用 **varId(整数)寻址**,服务端从 `config/io_config/*/io_config.json` 建 id→{fullPath,命令/观测} 索引。真机当前配置里**没有 6009/6010(相机触发 DO)**,它们只存在于主控枚举 io_var_id.h(占位"实际 id 待确认")。**中转层的 io 配置 = 一份自定义 varId 目录**,只需覆盖主控流程实际用到的变量:

| varId(主控枚举) | 名称 | io 类型 | 映射到 28 模型 | 动作 |
|---|---|---|---|---|
| 6009 | DO_PLC_CamUp_Trigger | PLC DO | `SystemMachine.SS_Bonding.M_AS.AlignCameraTigger_1`(→相机 up) | SetBool true → 28 拍照 |
| 6010 | DO_PLC_CamDown_Trigger | PLC DO | `...M_AS.AlignCameraTigger_2`(→相机 down) | 同上 |
| 6000~6008 | 真空阀 Close/OpenNegative/OpenPositive(BH_YN_XN/BH_YP_XN/FA_*) | PLC DO | `...M_AIR.WT_BondingVac_1/2、ChuckVac` 对应命令+AirRoute* 观测 | POST /api/io/command |
| 2000~2003 | DI oYN_XN_WithChip 等 | PLC DI | `/io/observe` 读对应观测点 | 只读 |
| 0~4(AI)/4000~4002(AO) | 干涉仪/WS 水平台 X/Y/Rz | PLC | `/io/observe`(AI)、SetValue(AO) | 读写 |
| 其余任何 varId | — | — | **回 errorCode=1(查无此变量)** —— 与真 io 服务对未知 varId 的行为一致,主控按失败处理,不会卡死 | — |

- **写语义与 verify**:主控 `SetDo(varId,value,verify=true)` 期待收到 `IOSetCompleted{varId,success,errorCode}`。中转层流程:执行 28 命令 → 若 verify=true,回读观测(SetBool 镜像点 `o<叶名>` 或指定 observer)直到等于期望值或超时(真机 20s)→ 发 SetCompleted。
- **相机触发的特殊处理**:28 的 `AlignCameraTigger_1/2` 是命令点,`SetBool true` 立即触发 `engine.camera_trigger` 并(如用 Pulse)0.5s 后自动回落。中转层对这两个 varId **收到写入即视为 PLC 已消费**,立刻回 `IOSetCompleted(success)`,不必等观测回读(观测窗口只有 0.5s,verify 每 100ms 轮询可能错过,且触发成功才是业务语义)。
- **IOGetServerInfo**:返回目录里登记的 AI/DI/AO/DO/Setting/Cmd/Buffer 表(名称建议与 io_var_id.h 的 label 一致,方便 GUI 调试页),mctrl 端不校验 id/name 内容(GuiManager 全量透传),但**目录非空且结构正确**。
- **主动上报(复刻)**:1s `IOStatusUploadPublish()`(平台无参心跳,与真 io 服务端一致)、500ms `IOObserverDataPublish`(全量缓存)、verify 完成 `IOSetCompletedPublish`。

### 6.3 相机触发与视觉结果(master VSC/VSS ↔ 28 视觉)

**触发侧(拍照入口)只有一条真实链路:io DO 写**(需求指定的两个消息)。细节:

- 主控 `VisionManager::Capture(cam)` → `SetDo(6009|6010,true,verify)` → 中转 io 侧把 DO 翻译成 28 的 PLC 命令点触发 → 28 走"闪光→曝光→识别→发布 `vision/result/{cam}`"完整链路。
- 若主控是 **VisionCF_LOCAL_DEBUG 构建**(mctrl/CMakeLists.txt:32 当前默认 ON),每次 Capture 成功后还会向 `VSC_Com` 广播 `CamCaptureTrigger{camID}`。中转 MQTT 桥会收到它,但**同一相机在 io 触发后短窗口内(如 500ms)视为重复信号去重,不二次触发**(保证每次拍照恰好一次、结果 1:1)。【待确认】部署端主控是否带此宏,不带宏则不存在该消息。
- 相机映射:DO 6009→28 相机 `up`(AlignCameraTigger_1),6010→`down`(AlignCameraTigger_2);28 三相机还有 `coarse`(oAS_CameraOn,主控当前无对应流程,预留映射行)。

### 6.4 共焦(cf)(master CTL_WM_CF ↔ 28 confocal)

主控 CF 只实际使用一个命令:`CMD_CF_MeasureOneChannel {id:0, sensorId:N, collectionQuantity:M}`(sensorId 来自 MC 常数),且全局**同一时刻只允许一笔在途**(单飞,CFManager.cpp:256-257),期待回 `CMD_CF_MeasureOneResult {id:0, count:M, data:[µm×M]}`。28 模型对应 probe=up/down 的 `confocal` 单点读数。

映射:

| 主控请求 | 28 动作 | 主控回包 |
|---|---|---|
| CMD_CF_MeasureOneChannel{sensorId→probe(映射表), M} | 循环 M 次同步 `GET /api/confocal/read?probe=up`(每次一读数 µm;首选,简单可靠)或 MQTT `confocal/trigger/{probe}`→`confocal/result/{probe}` | `CMD_CF_MeasureOneResult {id:0,count:M,data:[...]}`(µm;无效读数填 0——mctrl average 会忽略 0 再 ÷1000 得 mm) |
| CMD_CF_Ininialize/Open/SetRunningParameter/... 生命周期类 | 不动作 | **原样回显 task + result=true + 空 context**(mockserver 先例;mctrl 对未知 task 忽略) |

- 结果回包**不带 sensorId**,主控靠"单飞记住的 pending sensorId"归属,所以桥必须**每笔请求恰好回一条**、绝不重复回(重复回会被当作新测量结果,静默错误)。
- 映射表:sensorId(主控 MC)→probe(up/down);当前流程 ChipPosCalib 用 down 传感器、调平用上/下传感器,实际 id 值以 MC 配置为准【待确认】。

### 6.5 状态同步与 UI 联动

- 主控 GUI 的位置/状态来自中转层 motion/io 的 **Observer 推送**;中转层数据来自对 28 `/api/axes`(与 `/io/observe`)的周期缓存轮询(200ms 缓存、500ms 推送)——保证主控 GUI 数字与 28 UI 动画一致(28 引擎 1ms tick,经 /ws 500Hz 直接驱动 HTML 前端,无需中转干预)。
- 28 前端 UI 是否"动起来"取决于 28 引擎是否收到 move——中转层把主控命令真正发给 28 即可,前端动画自动跟随。

## 8. 关键技术决策、风险与对策

### 8.1 MQTT broker / QoS 兼容(最高优先风险)

- 主控 MQTT 平台库默认 `Subscribe(qos=2)`/`Publish(qos=2)`(istar_mqttclient.h:42-48),但业务层走 ISTARIMqttWorker 封装(无 qos 参数),**实际上线 QoS 未定**;
- 28 模型 mini broker:**QoS2 发布只回 PUBACK 不转发**(mqtt_broker.py:258-259)。
- 对策(按序尝试):
  1. **零改动验证**:主控与中转都连 28 自带 broker(1883)。实测平台库发布/订阅的 QoS:若 publish≤QoS1、subscribe 能容忍 granted=0,直接可用。
  2. 若 QoS2 阻塞:**给 28 模型 mqtt_broker.py 补 QoS2 支持**(PUBREC/PUBREL/PUBCOMP + QoS2 转发,约 40 行,纯标准库,自带 selftest),并在其 开发交接.md 登记。**这是对 28 模型的最小可回退改动**。
  3. 兜底:让 28 模型 broker 端口可配(改 main.py 一处),1883 交给完整 broker(需引入第三方 broker 或自实现,工作量大,不推荐,除非 1/2 都失败)。
- 中转自己的 MQTT 调用**显式用 QoS0/1**,不依赖默认。

### 8.2 "有无片"等 DI 状态在裸驱动下不自动演化

- 28 模型的 `oYN_XN_WithChip` 等 DI 观测由 `engine.workpieces`/flow 内部状态驱动(workpieces.py、process_flows.py),**只在 28 自己跑流程/工艺时更新**;主控"裸驱动"轴与真空 DO **不会**让它自动变真/变假。
- 影响:主控流程中依赖 DI 有无片判断的步骤(如取放片校验)可能拿不到"符合预期"的反馈。
- 对策:本方案**验收口径**按需求原文("控制 28 模型界面运动、正确拍照拿结果、cf 结果")设定为**单步/半自动动作 + 对准/标定类流程**;全自动整片流程若需打通,属二期(可选:28 侧开 `POST /api/workpiece/*` 与主控动作同步,或直接调 28 的 `/api/flow/*` 流程级接口替代主控编排)。【需求评审点,见 §10】

### 8.3 主控相机/共焦的机器常数(MC)需与 28 模型几何对齐

- 主控把视觉像素坐标换算 mm 用 MC 常数:`dXmm=(posX−resX/2)*pixelSize/mag`、`dYmm=负`(GroupLocateSubProc.cpp:123-125)。28 模型相机:分辨率 3000×3000、up/down 像素当量 0.6µm/px、coarse 9.133µm/px。
- 若 MC(真 CTL_TL_MC 服务配置)的相机分辨率/像素当量/安装偏移与 28 不一致,换算出的台子坐标会偏。
- 对策:联调前做一次 **MC 常数对齐清单**:上下相机 cameraId=0/1(必须,见 §6.3)、分辨率、pixelSize、放大率、visionTimeOutMs、共焦 sensorId、相机安装偏移(与 28 vision_cameras.json / machine_constants.json 对照)。MC 属 EH/MC 服务配置(不在中转层内),此清单作为联调前置。

### 8.4 模板(template)体系

- 28 识别 FAST 模式不依赖模板;REAL 模式与流程依赖 `vision_templates.json` 里建好的模板名(如 cv_cross_0824/tpl_die_head...)。主控下发到视觉的模板名是它自己的 markId(如 "mark1"),两套体系无直接对应。
- 对策:中转不翻译模板(主控 PrepareTemplate 的 CamSnapOnce 仅记录);触发拍照由 28 用其机器常数/模板(FAST 模式几何出结果)自动完成。若 28 某相机 REAL/无模板导致空结果,回 judge=false 继续。**模板深度对齐留待联调按需处理**。

### 8.5 主控侧配置快照错位(已修正)

- 仓库快照 config2/config4 若干 plc json 的 `machinePartFullPath` 曾与文件名错位(ArmHead 三文件循环错位、FA_Rx/FA_Rz 交叉)——已于 2026-10 在 `config\motion` 修正为与文件名/表格一致。桥接按 stage 名映射,不受影响;`simulator\28module\部分接口信息\motion\` 下的接口快照仍带旧错位,需 28 同事同步修正。
- 28 模型 MCS fullPath 前缀 `3000_1_Controller` 注明"源自 3000 模板,1928 真机前缀待复核"(mcs_map.json:6);PLC 命令面(9102/io_points)无控制器前缀,从 `SystemMachine...` 开始,本方案相机/真空映射走**9102 命令面**,不受影响。

### 8.6 命令完成/位置精度的"真伪"

- 28 引擎到位 = 轨迹跑完 + 伺服 settling 50ms(|pe|<0.002mm/20µrad)。主控侧 tolerance>0 时按 \|pos−target\|≤tol 判定,tolerance=0 时"硬件 inPos"。中转默认用 28 的 `state==idle && in_position==true`;若主控流程对定位精度有更严要求,在映射表按轴补 tolerance。
- 28 `/api/axes` 无 acc 字段:Observer 的 acc[] 用速度差分或填 0(主控 GUI 基本不展示 acc)【待确认】。

### 8.7 心跳/超时细节

- mctrl 每 1s 发 GetServerStatusAsync,rcvtimeout 10s;中转 GetServerStatus 由接口库默认回 success(建议打日志)。
- PUB 心跳 1s、Observer 500ms 照 config 周期推;若中转长时间收不到 28(HTTP 挂了),Observer 继续推缓存值,心跳照发,避免主控误判"motion 进程离线"(motion 进程离线会触发 EH 告警/流程中断)。

### 8.8 端口占用与启动顺序

- 中转 RPC 服务绑定前,确认真 `CTL_MDL_IO.exe`/`CTL_MDL_Motion.exe` 已停;启动顺序:EH/MC/RP/RM → **28 模型(main.py)→ 5 个中转进程 → mctrl → GUI**(mctrl 启动即同步 GetServerInfo,下游先起避免 10s 超时降级)。

## 12. 范围裁剪与决策记录(2026-09-04 讨论)

主控方确认的范围优先级:

- **motion**:4 个模块全部运动台都可控;接口重点 `MoveAbs / Enable / 观测 / GetServerInfo / 心跳 / Observer / 命令完成`。Home/Stop/Jog/速度参数等**不裁剪**——28 侧自带 home/stop 语义与完成状态,转发+轮询成本低,一并实现。
- **vision / cf**:要求正确交互——触发拍照/触发采点并拿到结果(1:1 回包)。模板体系对齐仅按需(§8.4),不阻塞。
- **io**:仅需相机触发(DO 6009/6010→AlignCameraTigger_1/2)+ 服务端存活应答(GetServerStatus/GetServerInfo/心跳/SetCompleted)。其余 varId 一律回 errorCode=1("查无此变量"),**不模拟真空/DI**——意味着依赖吸盘/有无片反馈的完整自动工艺步骤不在本期范围。
- 联调前置确认项(非阻塞):①键合头/FA_Rz 的轴映射——已闭环(2026-10 真机 config 修正后与 §7 映射一致);②主控 MC 机器常数(相机参数)是否与 28 几何一致,决定像素→mm 精度(§8.3);③实际部署的 mctrl 是否带 `VisionCF_LOCAL_DEBUG` 宏(影响 CamCaptureTrigger 去重,双端兼容);④28 模型 broker 若需补 QoS2(§8.1)须经 28 同事同意。
