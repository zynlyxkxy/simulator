## 1. 全局地图：系统由哪几块组成，数据怎么流

### 1.1 一句话定义

这套系统是一台**"外部行为保真"的虚拟 D2W 键合设备**：上位机软件（整机软件、测校软件、面板、3D 模型）看到的指令面、反馈语义、时序、故障行为，与真机一致；内部物理是工程近似模型，不追求与真机内部结构 1:1。

### 1.2 进程与端口地图（一台电脑上跑全套）

要点：**所有端口背后是同一个进程、同一个物理内核**。轴在任何入口被移动，所有入口看到的反馈都一致——这正是真机的样子（真机也是一台控制器同时服务多条通讯通道）。

### 1.3 三条消费通道，按"谁在用"分

| 通道 | 协议 | 谁在用 | 为什么选它 |
|---|---|---|---|
| 9010 REST + WS | HTTP / WebSocket | 控制面板、3D 模型、测校作业 API、AI/脚本 | 工程效率最高：浏览器原生、调试可见、自描述 |
| 1883 MQTT | MQTT 3.1.1 线协议 | PyQt5 测校软件、视觉触发/结果、共焦 | **与真机测校软件同一线协议**——换 broker 地址即可上真机 |
| 9101/9102/9190 | TCP/HTTP 指令面 | 整机软件（经桥接程序） | 复刻真机下位机接口语义（点位表/Cordis MCS/ACS SDK） |

### 1.4 数据流的一个具体例子（下精对准一拍）

1. 测校 GUI 发 MQTT `VSC_Com`（VisionCmdJson，让 down 相机识别模板）；
2. broker 投递给 `mqtt_cmd_adapter`，转调视觉服务 `identify`；
3. 视觉服务向"相机"（9200 内部口）取一帧——REAL 模式下这一帧是**按当前整机位姿实时渲染**出来的（9MP、离焦、噪声全带）；
4. NCC 模板匹配得亚像素峰位 → `VSS_Com` 结果帧回给 GUI；
5. GUI 拿像素坐标经 `solve_pixel`（含相机常数、台位、微旋认知）反算世界坐标。

整条链与真机测校软件跑在真相机+真控制器上时**逐帧同构**——这就是"把 HTML 模型当已装配好的设备"能成立的原因。

## 2. 四条根本设计决策（理解这些，其余全是推论）

### 决策一：仿"外部可观测行为"，不仿"内部控制律"

真机 ACS 驱动器内部是 kHz 级三环 PID + 前馈；倍福 PLC 内部是 EtherCAT + 任务周期。**这些内部机制上位机永远看不到**——上位机能看到的只有：发指令 → 轴按某种时序运动 → 读数反馈 → 到位/超时/故障。

所以仿真只复刻这层"可观测外壳"：S 曲线规划器生成轨迹（像真机的规划器输出），一阶滞后模型模拟跟随误差与到位整定（像真机位置环的外部表现），PLC 扫描周期模拟"写入晚一个周期生效"。至于三环内部怎么算——不仿，也不需要仿。

> **为什么这是对的**：目的决定保真度。这套系统的目的是让上位机软件"在上面调试算法和流程"。流程与算法只消费外部行为。内部控制律保真度再高，对这个目的零贡献，还会把开发拖进参数辨识的泥潭。
> 详见 `仿真实现原理.md`（ACS/PLC 逐层对照表）与 `仿真差距与路线图.md` §3（质量把控原则）。

### 决策二：接口契约先行

项目的起点不是代码，是事实源：`1928运动固件点位表_V6`（下位机点位）、`部分接口信息/`（同事模板工程：RPC 契约、Cordis MCS 五服务、ACS 指令面、stage 划分）、`整机轴记录表_V2`（轴参数）。仿真对外暴露的一切——点位名、轴名、报文信封、错误码——全部以这些事实源为准，并固化在 `接口规范_V1.md`、`Cordis_MCS协议_V1.md`、`前后端数据协议_V1.md`。

> **为什么**：接口是多方协作的唯一对齐点。模型可以有 bug，契约不能有歧义。桥接程序能写出来，前提就是这三份文档先行存在。**现在的推论**：模型已上内网被真实消费，契约变更必须评估下游影响（交接文档 2026-10-12 条）。

### 决策三：真值/认知双层 + 误差注入

系统里同一个物理量有两份数据：

- **物理真值**（truth）：仿真内核"实际发生"的位置/温度/力——真机上是物理世界本身；
- **控制器认知**（belief）：经传感器、标定常数、读数链之后"上位机能读到"的值——真机上是编码器/传感器/标定表给出的世界。

两者之间是**误差链**：伺服重复定位、比例误差 scale_ppm、误差地图、相机安装旋转、噪声……全部以可配置旋钮注入。测校程序测的是认知，写回的是机器常数（认知侧的修正），闭环后认知逼近真值。

> **为什么故意注入误差**：没有误差的仿真只能验证"流程能不能跑"，不能验证"测校/补偿算法对不对"。测校前移——在模型上把标定流程、算法、数据记录全部验完——是这台模型最大的价值之一，而它的前提就是"误差要先进去"。
> 详见 `键合误差模型_V1.md`（truth 分量分解）、`前后端数据协议_V1.md` §10（机器常数 11 组）、`视觉系统_V1.md`（相机真值/认知三件套）。

### 决策四：一切改动可回归

`backend/tests/test_client.py` quick 套件 417 条用例（全量 457），日常 ≤3min 跑完，红线（tick 1000Hz / push 500Hz / 延迟）每次断言。每天 09:17 有 Windows 计划任务自动跑（`D2W_DailyRegression`）。

> **为什么**：39 天 57 个迭代不崩盘的制度保证。每次改动后"没有弄坏旧功能"不是靠记忆，是靠套件。同事在桥上踩出的任何模型 bug，修复后都会变成套件里的一条新用例，防再发。
> 详见 `回归基建_V1.md`。

## 3. 实时内核：1000Hz / 500Hz 是什么、为什么是红线

- **物理 tick = 1000Hz**：每 1ms 推进一拍——轨迹积分、伺服滞后、IO 物理（气路惯性、温控、力）、碰撞检查、误差注入全在这一拍里。选 1kHz 是因为真机控制器就是 kHz 级节拍，太快没意义、太慢会让"扫描周期""整定延迟"这类时序语义失真。
- **WS 推送 = 500Hz**：3D 模型与面板的轴位置流每 2ms 一帧（108 字节二进制帧，21 轴）。500Hz 对显示绰绰有余，同时压得住 CPU。
- **PLC 扫描 = 4ms**：模拟倍福任务周期——写点位最晚 4ms 后生效，观测按扫描率采样。上位机轮询/超时的设计必须容忍这个粒度，真机上一样。
- **伺服整定 ≈ 50~70ms/次**：S 曲线跑完 ≠ 到位；还要等跟随误差收敛进窗口（in_position）。所以流程里"move 之后立刻拍照"在仿真里会真实地吃到整定延迟——真机同款。

> **红线**：本机单向延迟 p50<1ms、tick/push 不许退化。桥接程序如果在内网另一台机器上跑，网络本身会增加毫秒级延迟——这是部署环境差异，不是模型变慢，排查时先分清楚。

| 主网关 | 9010 REST+WS | 面板/3D/测校作业/机器常数/故障注入/热模态开关 | `前后端数据协议_V1.md` |

### 4.2 必知约定

- **单位**：全线直线 mm、旋转 rad；µrad/µm 只出现在显示层。唯一例外：TwinDOM 前端模型内部是 deg，换算只发生在 `html_model/联机注入.js` 边界——桥接程序不需要碰这个。
- **MQTT 版本**：broker **仅支持 3.1.1**。MQTT 5 客户端直连会被拒（CONNACK rc=1），客户端改 3.1.1 即通。这是同事联调已经踩过一次的坑。
- **错误语义**：非法运动/干涉/联锁 → 409；参数非法 → 400；MCS 面映射真机式 FAULT body。
- **过渡协议声明**：9101/9102 是自定义过渡协议（真机 ACS SDK 私有协议、PLC 真通讯方式待确认），语义已按事实源对齐，线格式将来加适配层。9190 MCS 面则是按同事模板工程逐字段复刻的真契约。
- **故障注入面**：`POST 9010 /api/fault` 可以模拟掉使能/沉默/断线——上位机的超时、看门狗、重连逻辑应该在仿真上先考一遍，这是这套系统专门为整机软件准备的能力。

## 5. 视觉系统：为什么有 FAST / REAL 两种模式

三相机（up/down/coarse），up/down 是 600nm/px 的精密对准相机（3000×3000，FOV 1.8mm），coarse 是 9.13µm/px 的粗对准相机。

- **FAST 模式**：识别结果**解析直出**（真值+噪声直接算出来），不渲染图像。快，用于测试套件和不需要图像语义的流程验证。
- **REAL 模式**：按当前整机位姿**渲染一帧真实图像**（标记精灵光栅化、景深离焦模糊、雪花噪声、亚像素平移注入），然后跑真 NCC 模板匹配。单拍 0.6~1.6s，行为与真相机链同构。

**相机真值/认知三件套**（同事最容易问到的点）：

- `view_rot_deg`：相机**物理安装旋转角**（真值，只影响渲染出来的图像）；
- `rot_mrad`：控制器**认知**的旋转角（机器常数，只影响像素→世界的反算）；
- `dir`：图像轴相对世界轴的方向（+1/−1），默认 (+1,−1) 对齐真实相机朝向。

物理转正（改 view_rot，图像不再旋转）和认知补偿（改 rot_mrad，计算修正）是**二选一**的两种标定路线，都做就是双重补偿——微旋标定测校项的文档（`相机微旋转角标定_V1.md`）有完整推导。

> **血泪教训（写进制度的）**："FAST 过 ≠ REAL 过"。REAL pi（键合后检测）曾静默失效六个迭代，因为测试套件全跑 FAST，而用户面板默认 REAL。现在 REAL 链有成对回归哨兵。**推论给同事：在桥上验视觉相关流程，默认用 REAL，FAST 只用于提速的场景要明示。**

## 6. 误差注入与机器常数：测校为什么能在仿真上做

- **误差链**（`error_kinematics`）：每轴 actual = 伺服实际位 + 重复定位（到位重采样）+ scale_ppm + 误差地图分段插值；模块级还有 6DOF 位姿误差链（工具点、链轴心等）。轨迹永远走名义值——和真机"规划是规划、实际是实际"一致。
- **机器常数 11 组**（`前后端数据协议_V1.md` §10 全表）：cameras / wafer_ega / flip_pick / flip_handoff / focus_level / fine_align / bond / stage_geo / bs_rxry_axis / sensor_calib / vision_marks。它们是真机上"标定表"的角色：测校程序的 measured 结果经 apply 写回这些常数，后续流程消费的就是写回后的认知。
- **闭环**：注入误差（真值≠认知）→ 跑测校（测出误差）→ 写回常数（认知修正）→ 复测（残差≈0）。这条链上已有 22 项测校 routine（面板工作台）+ 18 项 PyQt5 GUI 测校页，各自带独立技术文档。

> 同事若在桥上做"坐标系方向对齐与机械常数识别"，要跑的典型标定顺序（EGA 锚定、焦面、上吸盘锚点、旋转中心/增益、非正交、承接/键合高度、RxRy 轴、温度/力校准）在汇报材料 §四.3 和各测校文档里有 SOP。

## 7. 热仿真与模态仿真：两个"默认 OFF"的工程近似层

这两层是**可插拔的保真度增强**，默认关闭（保证日常行为确定性和性能红线），面板顶栏开关热切换。

**热仿真（`热仿真_V1.md`）**——LPTN 集总参数热网络。用电路类比：温度=电压、热流=电流、热容=电容、导热=电导。168 个组件归并成 21 个节点，节点间三类耦合：传导（固定电导）、加热器锚定（温控环）、辐射链（视角系数随轴位实时变化——热头压近相机会真的加热相机承载台）。温度再经 deform_map（6 条：膨胀/弯曲/吸盘 Z 胀…）变成 6DOF 热变形，贯通进对准与键合真值。

**模态仿真（`模态仿真_V1.md`）**——21 轴 SISO + 9 个全机 MIMO 模态的状态空间 ROM，三类激励（地板振动/接触脉冲/轴运动余振），对视觉还有曝光积分效应。整机一阶模态 18~110Hz，贴合行业调研口径。

> **对同事的一句话**：这两层 OFF 时模型是"理想刚体+理想温度"；ON 之后能看到热漂移、振动余振这类慢效应。参数全部是工程估值（CTE/电导/模态频率），**量级可信、精值待真机标定**——这是刻意声明的边界，不是隐瞒。

## 8. 工艺流程与物料：flow_engine 扮演谁

真机上工艺流程编排是 L2 主控层的活；仿真里 L2/L3 未拆进程，`flow_engine` + `flows.json` 先把这个角色演了——19 步示范流程（上片→取片→交接→对准→键合→下片）本质是一份**可执行的验收脚本**。

两个值得知道的机制：

- **transfer 宏与物料守恒**：交接（蓝膜→翻转→键合头→晶圆）由引擎按"真空/正压+示教位"上升沿真实换载体，流程层只凑条件不偷改状态；蓝膜计数全程守恒（中断留片也有明确语义）。迭代 76 起，键合头任一路正压可在非流程/高位按实际 XY 垂直落片；有效翻转承接仍优先，手动落片不等于热压键合成功。
- **沙盒干涉**（`collision`）：146 个零件级包围盒、872 有效对，穿模深度 >2mm 判撞——move 起步 409 拒绝，运动中撞入全轴 soft-stop。它和真机"软件禁区"同层；机械限位与力控接触段是另外两层，语义也分别在。

## 9. 测校体系：为什么是"面板 + PyQt5 GUI"双客户端

- **面板测校工作台**（HTTP 作业 API，22 项 routine）：工程效率优先，浏览器直达，适合快速验证与演示。
- **PyQt5 测校软件**（18 项，MQTT 线协议，复刻真机测校框架分层）：**按真机标准做**——线协议、信封、超时、数据落盘全部与参考框架同构，将来换 broker 地址即可上真机。它是"测校分系统验收平台"的载体。

两条链并存是有意分层：真机上没有 `/api/calibration`，真机测校只能走 MQTT 原语。GUI 侧踩过的坑（MQTT 积压、接收线程死亡、首拍 (0,0)）已全部修掉并固化为防线。

## 10. 回归基建：为什么每次改动都要跑套件

- quick 417 条（≤3min 目标，当前机器 ~15min 内属正常负载波动）覆盖全部核心行为；全量 457 条用于交付/接口变更前。
- 性能红线（tick 1000Hz / push 500Hz / p50<1ms）每次断言，退化即 FAIL。
- 已知 flake（负载敏感的时序用例）有轮换清单与定向复跑规程，不要把 flake 当回归、也不要把回归当 flake——判别方法在 `回归基建_V1.md` §6。
- 每天 09:17 计划任务自动跑 quick，日志落 `Temp/regression_logs/`。

> 对桥接时代的意义：同事反馈"模型行为不对"时，第一动作是**先跑套件确认基线是绿的**，再复现取证——定位效率差一个数量级。

## 11. 同事常见问题预演（FAQ，可打印）

**Q1：桥接程序该连哪个口？**
取决于对接哪一层：运动指令走 9101（或 MCS 面 9190，真机契约）；IO/气路/温控走 9102；视觉与测校原语走 1883 MQTT。层间对应关系看 `接口规范_V1.md` §1 的表。

**Q2：为什么 move 指令不是瞬间到位？**
S 曲线规划 + 伺服整定（到位窗口收敛 ~50~70ms）+ PLC 扫描 4ms 粒度。真机同款时序。流程里 move 后必须等 in_position。

**Q3：为什么每次读数不完全一样？**
误差注入在工作：重复定位 3σ、噪声预算、误差地图。这是特性不是 bug——测校算法要考的就是它。需要"理想值"时可把对应旋钮归零（config_overrides），但默认配置就是有误差的真机样子。

**Q4：拍照为什么要等？为什么会失败？**
REAL 模式单拍 0.6~1.6s（真渲染真匹配），上限 12s。两个前提：光源要先点亮（点位 LightOn 系列）、模板要先建库。FAST 模式不等，但没有图像语义。

**Q5：温度/力为什么有惯性、爬得慢？**
PID + 一阶对象 + 热惯性是刻意建模的真机行为。温控脉冲加热 200℃/s 只是指令面，对象响应有自己的时间常数。

**Q6：MQTT 5 客户端连不上？**
broker 仅支持 3.1.1，改客户端协议版本即通。

**Q7：单位是什么？**
直线 mm、旋转 rad，全线统一。µm/µrad 只用于显示。

**Q8：图像方向/坐标系对不上？**
先查三件事：dir（默认 +1,−1）、view_rot（物理装旋）、rot_mrad（认知）。三者关系见 `视觉系统_V1.md` 与 `相机微旋转角标定_V1.md`。

**Q9：模型会"撞机"吗？**
会——而且应该让它撞：沙盒干涉 409/全轴急停就是为了让上位机把回避逻辑调对。已知边界：薄片穿刺（≤2mm 阈值语义）与旋转扫掠盒的保守外扩。

**Q10：仿真的精度数字能当验收指标吗？**
不能。流程、算法、通讯、数据记录可以在仿真上验收；**精度类指标一律以真机实测为准**。模型里的热/模态参数是工程估值，量级可信、精值待标定。

**Q11：怎么考断线/掉使能/固件挂死？**
`POST 9010 /api/fault`：轴级 disable/fault/reset_error，目标级 silent（吞指令）/drop（断连）。上位机的超时与重连逻辑应该在仿真上先考合格。

**Q12：怎么回到干净状态？**
`POST 9010 /api/full_reset`（键合历史一并清零）；机器常数/处方走各自 API 的 restore。
